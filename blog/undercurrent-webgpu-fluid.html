Undercurrent — WebGPU Fluid Simulation

A real-time GPU fluid solver built with TSL node graphs. This case study walks through the architecture, performance budget, and the compromises we made to hit 60fps on mid-range hardware.

The brief

The client wanted a portfolio hero that felt "alive" — not a video, not a canned animation, but something that responded to input in real time. The constraint: it had to run on integrated graphics without dropping below 60fps.

We proposed a Navier-Stokes-inspired fluid simulation running entirely on the GPU via WebGPU compute shaders. The visual target was dark, iridescent, with a sense of depth — ink in water, but with light sources inside the flow.

Architecture

The simulation uses three ping-pong render targets: velocity, density, and pressure. Each frame runs a five-pass pipeline:

  1. Advection — semi-Lagrangian, samples previous velocity field
  2. Forces — mouse input injected as velocity impulse
  3. Divergence — compute velocity field divergence
  4. Pressure (Jacobi, 20 iterations) — solve pressure Poisson equation
  5. Projection — subtract pressure gradient from velocity

The density field is advected by the velocity field and rendered with a custom iridescence shader — thin-film interference approximated via a lookup table.

"The key insight was using TSL node graphs instead of raw WGSL. We could iterate on the shader in TypeScript, with type safety, and the same code compiled to both WebGPU and WebGL2 fallback."

— Lead engineer

Performance budget

Target: 60fps on Intel UHD 620 (lowest supported). Budget per frame: 16.6ms.

PassTime (ms)Notes
Advection1.8512×512, bilinear sampling
Forces0.3Single dispatch, mouse uniform
Divergence0.99-tap stencil
Pressure (×20)7.220 Jacobi iterations × 0.36ms

The compromise

We cut the simulation grid from 1024 to 512. The visual difference was minimal — the iridescence shader masks the lower resolution — but the performance gain was 4×. On high-end hardware, the grid scales up to 1024 automatically via a capabilities check.

The WebGL2 fallback uses a CPU-side Jacobi solver at 256×256. It's 30fps instead of 60, but the visual identity holds. Users on Safari pre-WebGPU still get a fluid hero, just slower.

What we learned

TSL node graphs are the real deal. The ability to write GPU code in TypeScript, with autocomplete and type checking, changed how we iterate. A shader bug that used to take 20 minutes of `console.log` triangulation now shows up as a type error in the editor.

The five-pass pipeline is harder to debug than a single shader, but the separation of concerns (advection vs. pressure vs. render) made it possible to tune each pass independently. The performance budget table above was the single most useful artifact — we knew exactly which pass to optimize when frame times slipped.
